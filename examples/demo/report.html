Security

rubric 1.0.0

Any caller can read any note and any file under the service directory; fix both before exposing the service.

Two problems are reachable without credentials: the note-by-id route returns notes of other users, and the export route builds a file path from the URL. The service trusts an x-user header as identity, which makes both worse. Request bodies are parsed as JSON with the framework default limit, and no secrets are tracked. Nothing was executed, so runtime behavior behind a proxy is not confirmed.

Findings

HighExport route reads files outside the exports directoryF-001
What was found
GET /export/:file concatenates the URL segment into a filesystem path and passes it to sendFile without normalizing or confining it.
Why it matters
An unauthenticated caller can request encoded parent segments and read any file the process can read, including source and environment files. It does not allow writing files.
What to do
Resolve the requested name against the exports directory and refuse anything that leaves it; prefer the root option of sendFile. Keep the route read-only.
Affected
File export
Evidence
  • src/server.js:20
  • src/server.js:19
How to verify the fix
  • A request for an encoded parent path returns 400 or 404.
  • A test requests a file outside exports/ and asserts it is refused.
Verification pass
confirmed, high confidence. Re-read src/server.js:19-21; no normalization, no root option, no allow-list on this path.
HighA note can be read by id without checking its ownerF-002
What was found
GET /notes/:id returns readNote(id) directly; the list route filters by owner but the single-note route does not.
Why it matters
Any caller can enumerate ids and read every user's notes. Ids are sequential, so enumeration is trivial.
What to do
Check the note owner against the caller in the route or in readNote, and return 404 for notes of other users.
Affected
Reading notes
Evidence
  • src/server.js:10
  • src/store.js:8
  • src/store.js:13
How to verify the fix
  • A request for another user's note id returns 404.
  • A test creates notes for two users and asserts the cross-read fails.
Verification pass
confirmed, high confidence. Re-read src/server.js:9-13 and src/store.js:8-10; no owner comparison anywhere on the path.
MediumCaller identity is taken from a client-supplied headerF-003
What was found
Routes use the x-user request header as the user identity; nothing in this repository authenticates it.
Why it matters
A caller can act as any user by setting the header, unless a gateway outside this repository strips and sets it. That gateway is not visible here.
What to do
Authenticate in the service, or document and enforce that only a trusted proxy can reach it and that it overwrites the header.
Affected
All note routes
Evidence
  • src/server.js:7
  • src/server.js:16
How to verify the fix
  • Requests without a valid credential are rejected with 401.
Verification pass
severity lowered, medium confidence. Lowered from high: a deployment behind an authenticating proxy is plausible and cannot be ruled out from the repository. Re-read src/server.js:1-23.

Open questions (not scored)

  • No request rate limit. No limiter is configured, but no concrete abuse path beyond the findings above was traced.

Tests

rubric 1.0.0

The suite would not catch a broken route or a broken ownership rule: only the in-memory store has tests, and one of the two is decorative.

Two tests exist, both for the store. Nothing exercises the HTTP routes, so the two security problems found in the security audit could be introduced or fixed without any test changing. The suite runs from a documented command and is deterministic. Coverage is not measured.

Dependencies

rubric 1.0.0

Installs are not reproducible: there is no lockfile, and one script downloads a tool at run time.

The project declares one runtime dependency with a caret range and tracks no lockfile, so two installs can differ. The export script runs a tool through npx that is not a declared dependency. No scanner was available, so the state of known vulnerabilities is not established.

Findings

HighNo lockfile is trackedF-001
What was found
package.json declares express with a caret range and the repository has no package-lock.json; the README tells users to run npm ci, which requires one.
Why it matters
Installs are not reproducible and the documented install command fails on a clean clone.
What to do
Generate and commit package-lock.json and keep npm ci as the documented command.
Affected
Installation

MediumExport script downloads an undeclared tool with npxF-002
What was found
The export script runs npx json2csv-cli; the package is not in dependencies or devDependencies, so npx resolves and downloads it at run time.
Why it matters
Whatever version the registry serves runs with the developer's permissions. Reach is limited to machines that run the export script.
What to do
Declare the tool as a devDependency so it is pinned by the lockfile, and call it through an npm script.
